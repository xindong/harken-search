# Harken Search 正式发布

本页属于 Harken Search 仓库，只在本仓库的发版任务里生效；它补充 Cuevi 发布门槛里的「项目专属」部分，不替代授权与验收收尾。公告内容、署名、样式和基线只维护在资产库的 `Skill库/release-owner/references/harken-search-updates.md`，不在这里维护第二份。括号里的日期是用户原话的出处。

## 授权与冻结

- 正式发布、补发、撤回分别需要本次明确授权；先确认版本、渠道、目标与动作。收尾不包含任何公开写入；预览同意也不等于上线同意。
- 对外写入前回读本项目发布窗口、冻结状态和审批，不把未读到状态当作未冻结。冻结中仅按项目正式机制取得本次有效的解冻或例外；已签名、紧急补发或撤回也不是绕行理由。冻结最终拟发 SHA、产物摘要、公告预览与通道；变更后重验、重签（产物变更时）并重新确认。

## 硬规则

1. **先预览再发。** 线上发布前，在本机打开官网公告和客户端公告预览；用户对**这一版**明确说「发布 / 可以发」才发。只说了「发布」而没看过这一版，不算。（2026-10-28；2026-11-25 09:35）
2. **三件同一次交付：安装包、客户端更新公告、官网公告。** 缺任何一端或两端不一致，就不算发布完成，也不切公开版本指针。（11-24 22:15「强行同步发布这是必须的」；11-25 01:12「我已经说了很多遍了」）
3. **公告写法、署名、样式与数据源**按上面的唯一权威正文执行，不在这里维护第二份。
4. **公告差集的基线用实际稳定包，** 不用首个同名 Actions 构建或源码里的版本常量代替。做法见参考文件「基线」。
5. **不跑 COS 旧版自动升级实测，也不用别的夹具顶替。**（11-25 01:14 用户取消）保留：自动更新功能、正式签名、包完整性与摘要、发布后版本/下载/公告回读。发布后用正式包更新本机并读 EXE 版本，这一步不叫旧版自动升级实测。
6. **版本号不复用。** 某号码在 GitHub Release 或 COS 写入过对象就永久占用，同名对象不能用不同字节覆盖。撤回只撤入口、不删包、不发「同号修订版」，修好后用下一个号（1.0.46 撤回后改发 1.0.47）。
7. **走受保护流程。** PR 合入 `qa/current`，再 `qa/current → main`；禁止直推 main 和 force；必检与 CodeQL 通过，审查线程逐条回复并解决；正式构建从最终 main 的精确 SHA 发起。
8. **签名与凭据。** 用公司 npkg 签名，需要内网或 VPN；凭据只走保密输入或既有加密配置，不进聊天、日志、代码。缺登录时说明需要登录的系统，交用户走正规登录流程后再继续。发布器位置用 `git config --local --get harken.publisherRoot` 读取，不另装；入口能打开不等于有签名或发布权限。
9. **失败不推进。** 签名、实际分发包、版本或公告回读任一失败，上一个正式版继续是正式版；先查清发布到了哪一步，再用原入口补齐，不盲目重发。

## 先核 Mac 覆盖（挡在发布前面）

发布前把本版本要上的东西逐项对一遍 Mac 版本，不能默认它跟上了。没有真实证据的写「未核实」，不得写成已覆盖。

1. 从本版本合进 `qa/current` 的卡和提交里抽出用户可见的功能变更（界面、交互、搜索、播放、导入导出、设置项），列成清单。
2. 逐项给结论，只写三种：已实现、未实现、不适用（纯 Windows 侧）。
3. 未实现的：在 Cuevi 里挂或开 Mac 卡（没就开，有就关联，不重复建），并在发布说明的已知差异里写清。纯 Windows 专属的能力也要写明，不让用户以为两端一致。
4. 两端公告和下载页面不能暗示 Mac 已有未实现的能力。这一步核完才能进下面的构建与签名。

## 步骤

0. **先对齐事实，一次说完。** 当前正式版（COS stable 清单）、已占用的号码（GitHub tags 与 COS `versions.json`）、拟发版本、源码里的版本常量是否一致、公告基线、发版卡号。只在版本号有歧义或缺授权时才问用户。
1. **版本与公告。** 版本号同步到 `CMakeLists.txt`、`src/Version.h`、`resources.rc`、`installer/HarkenSearch_Setup.iss`、发布说明。按公告权威正文修改同一数据源，只做最小行改动。用 `tools/build_release_catalog.py --source <回执 JSON> --output <catalog.json>` 生成目录，再用 `tools/website_release_page_preview.py --catalog <catalog.json>` 在本机打开官网页预览；客户端公告同源核对分组、顺序、署名。预览交用户确认。
2. **本卡验证。** 在发版卡的独立目录跑版本一致性、`tools/check_release_compliance.py`、`tools/verify_release_assembly.py`（相似音效资产见 `docs/similarity-release-assets.md`）和与发布相关的测试。全量 Python 不全绿就写清差异来源，不写「全绿」。
3. **合入。** 按硬规则 7。必检或 CodeQL 因外部原因没跑（例如 GitHub Actions 预算耗尽）时，写明事实并停在合入前，不绕过，也不把没跑当通过。
4. **构建与签名。** 从最终 main SHA 触发正式构建，再按发布器六步走：获取构建列表 → 下载产物 → 人工审核 → 数字签名 → 发布前校验 → 上传发布。优先使用发布器已配置的 Harken GUI。若用 CLI，先核对 `main.py --help` 和发布器配置；每条命令都在子命令前显式传 `--source-repository xindong/harken-search --branch main`，并核对 bucket、COS 前缀和公开地址，不沿用 CLI 默认的 `xindong/aris`。实际子命令依次是 `list-runs`、`fetch <run_id>`、`review <run_id> --confirm-reviewed`、`authenticode <run_id>`、`prepare <run_id>`、`publish <fixture> --dry-run`；先演练并回读，再执行正式上传。本机候选包只用于预览和自查，不是发布物。
5. **发布与回读。** 顺序是：版本文件可下载 → 官网版本索引 → 客户端 latest 清单。逐项回读 GitHub Release（`v<版本>`）、COS 对象、官网默认下载与版本索引、应用内更新说明和官网公告，核对版本、构建、哈希、签名者（`X.D. Network Inc.`）和正文一致。
6. **本机更新与记录。** 用正式包更新本机，读取实际 EXE 版本并验证签名与完整性。在 Cuevi 发版卡记录实际结果（含未覆盖项），证据放 `D:/Harken-QA/<日期>-release-<版本>/`，保留 7 天。需要结卡时回到 Cuevi 收尾技能，单独按可信完成及归档门槛执行。

## 预发布通道（1.0.47 起，可选）

构建选项 `ARIS_UPDATE_PRERELEASE_BASE_URL`；运行时 `ActiveMirrorBaseUrl()` 按用户名白名单（`zhongziyu001`、`zhongziyu`）切换镜像前缀，读设置和保存设置时重算，切换后提示重启生效；预发布包的启动器清单地址按当前通道校验。用途是让白名单内的开发者自己的安装读取预发布前缀，不翻公开 stable 指针。它不是放行门槛，不对白名单外用户开放。细节见提交 `0a7a4e9` 与 `src/update/UpdateReleaseConfig.h`。

## 补发

先查 GitHub、COS、官网与客户端的原版本回执，明确实际缺项、对应签名包和已上线状态。只补已有版本的缺项时，先预览并获该版明确的补发授权，按原正式入口补齐，与原签名发布回执和单一公告源对齐；不覆盖已发布资产、不变相换包。需改包、改已占用对象的字节或修复被撤回的版本时，用下一未占用版本重新走正式发布，不把补发当作复用同号的许可。

## 撤回

只撤入口，不删包，不覆盖不可变的同名文件，不强制降级已升级用户，不发「修订版同号」。先回读当前公开入口，并核实发布器是否已有支持本次撤回的正式入口；原流程记录中，发布器 README 写着稳定版回滚界面尚未实现，`release_update.py rollback-check` 也只是检查，不能当作撤回执行器。没有正式入口时，保留现场并如实报告缺口，不占共享发布锁、不手写上传。若正式入口已具备，先备份仍可见的版本索引和旧指针，再按其流程撤下该版；回读官网默认下载、版本索引（含根 `/versions.json` 与 `/aris/versions.json`）、canonical 与 legacy 两条 stable 清单都回到上一版。无法停用的直链单独列出，不写「撤干净」。签名包和回滚记录完整保留。（出处：BUG-20261124-RELEASE-1046-WITHDRAWAL）
