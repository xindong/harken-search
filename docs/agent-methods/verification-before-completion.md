# 完成前验证

任何“完成”“修复”“通过”“可以合并”的说法，都必须有本轮新运行的证据。旧日志、上一轮截图和“代码看起来对”都不够。

## 逐项取证

1. 写出结论需要哪条命令或操作证明。
2. 完整运行命令，不只看最后几行。
3. 检查退出码、失败数量和关键输出。
4. 将实际输出与结论逐项对照；不满足就照实报告。
5. 检查 git status、git diff --check 和改动文件清单。

## 不同结论对应的证据

| 结论 | 最低证据 |
| --- | --- |
| 测试通过 | 相关测试本轮运行，退出码为 0，失败数为 0 |
| 构建成功 | 对应目标本轮构建完成，退出码为 0 |
| Bug 修复 | 原问题的回归测试通过，并覆盖真实失败路径 |
| UI 验收通过 | 本次实际 QA 包的截图、操作结果和用户明确确认 |
| 可以合并 | 前述证据齐全，且当前分支和 QA 基线已按流程核对 |

## 报告限制

- 没有跑到的测试写“未覆盖”，不要写成通过。
- 只验证了逻辑时写“逻辑验证通过，界面待确认”。
- 发现环境阻塞时用中文说明发生了什么和下一步，不用“已修复”掩盖阻塞。
- 证据必须能对应代码版本、QA 包路径和测试数据；不要混用其他卡片的包或截图。
