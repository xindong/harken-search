# TDD：先红、再绿、再整理

TDD 用来把用户能感知的行为和边界写成可重复的检查。小改动也遵循同一顺序，避免“代码改了但没有证明原问题被覆盖”。

## RED：先写会失败的测试

- 测试名称写清行为，不只写函数名。
- 测试包含正常路径、这次 Bug 的失败路径和一个关键边界。
- 先运行测试，确认它因为旧行为失败；如果一开始就通过，说明测试没有锁住问题。
- 记录失败输出，不删除失败历史。

## GREEN：只做最小实现

- 只修改让测试通过所需的模块。
- 保留现有数据库结构、取消生命周期和其他功能，除非需求明确要求改变。
- 失败结果要有明确状态；不能用默认值、空向量或假成功填平失败。
- 运行刚才的回归测试，确认从 RED 变成 GREEN。

## REFACTOR：在证据之后整理

- 只有测试已经通过后才整理重复代码、命名和注释。
- 整理不能改变验收范围；整理后再次运行同一组测试。
- 如果测试、代码和文档描述不一致，先修正文档或测试，再继续。

## Harken 的测试分层

- 单元测试：验证一个函数或状态转换。
- 模块测试：验证数据库、搜索、音频分析、扫描等模块的边界。
- 行为契约测试：验证源代码仍保留用户承诺的交互和文案。
- 实际 QA 包：验证真实数据、真实窗口和真实运行时状态。

编译成功只说明代码能生成，不说明功能正确；模拟数据通过也不能替代真实素材库验收。
