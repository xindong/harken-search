# 系统排查

适用于 Bug、测试失败、构建失败、性能异常和“点击后结果不对”。核心要求是：没有根因证据，不开始修复。

## 1. 先确认问题确实存在

- 记录用户看到的现象、触发步骤、实际输入、预期结果和实际结果。
- 先看完整错误信息、退出码、日志和相关路径，不跳过警告。
- 用最短步骤复现；能稳定复现才进入修复，不能复现就先补数据和日志。
- 检查最近改动、配置、构建版本和运行数据是否一致。

## 2. 画出数据经过的路径

对跨层问题逐层核对：输入进入哪里、输出从哪里出来、状态在哪里保存、失败是否被吞掉。常见路径包括：

用户操作 → 界面状态 → 后台任务 → 数据库或文件 → 返回结果 → 界面提示

在每个边界记录关键值，直到找到第一个错误值出现的位置。修复第一个错误值的来源，不只改最后一个提示。

## 3. 对比能工作的路径

- 找一个同类但正常的功能或测试。
- 逐项比较输入、状态、返回值、取消路径、错误处理和持久化行为。
- 特别检查“返回值被忽略”“失败仍推进成功计数”“空集合被当作完成”等差异。

## 4. 形成单一假设并验证

把假设写成一句话，例如：“我认为写入返回值被忽略，因为失败后成功计数仍增加。”

- 只做最小验证，不同时改多个位置。
- 假设不成立就回到证据阶段，换一个假设；不要在旧修复上继续叠补丁。
- 连续三次修复仍失败时，停下来检查模块边界或共享状态是否设计不合理。

## 5. 修复顺序

1. 写最小的失败回归测试。
2. 做一个只解决根因的改动。
3. 运行回归测试和受影响的邻近测试。
4. 按完成前验证取新证据。

如果问题来自环境而不是代码，也要记录已排查的范围、最终采用的环境处理和以后如何识别它；不能把环境问题说成代码已修复。
